# Contributing to Fuji

Thanks for your interest in improving Fuji! Fuji is a patch-based fork — **[Leaf](https://github.com/Winds-Studio/Leaf)
`ver/1.21.11`** with every **[Sakura](https://github.com/Samsuik/Sakura) `1.21.11`** patch folded in — so contributing
looks a little different from a normal repo. This guide gets you set up.

## Before you start

- **Bugs / features:** open an issue first (use the templates) so we can discuss scope before you write code.
- **Cannon mechanics** are version-accurate via Sakura's `MinecraftMechanicsTarget`. If you touch cannon-entity
  movement, explosions, or merging, test against real cannons — these paths are easy to break subtly.
- **Per-world config:** gameplay/combat options live in Sakura's per-world `WorldConfiguration` (`sakura-world.yml`),
  not the global Leaf config. Prefer per-world for anything players might want to vary between worlds.

## Requirements

- A **Java 21+** JDK (Temurin recommended)
- **Git**
- On **Windows**: run Gradle from **Git Bash**, and enable long paths — `git config --global core.longpaths true`
  plus the `LongPathsEnabled` registry key — or paperweight will hit the 260-char path limit.

## Building

```bash
git clone https://github.com/BadgersMC/Fuji && cd Fuji
./gradlew applyAllPatches            # materialize the Leaf + Sakura source
./gradlew createMojmapPaperclipJar   # build the runnable jar (in leaf-server/build/libs/)
./gradlew runPaperclip               # spin up a test server
```

## Making changes (the patch workflow)

Fuji's source is generated by applying patches. After `applyAllPatches`, the materialized Minecraft source lives in
`leaf-server/src/minecraft/java/` and is itself a git work-repo. The cycle:

1. Edit the materialized source (or a `src/main/java` file directly for Leaf/Fuji's own classes).
2. **Commit your change inside the work-repo** (`leaf-server/src/minecraft/java/.git`).
3. Regenerate the patch files: rebuild the channels **individually** with `--no-configuration-cache` —
   `rebuildMinecraftFeaturePatches`, `rebuildServerFeaturePatches`, `rebuildPaperApiFeaturePatches`.
   (The umbrella `rebuildPatches` trips a Gradle 9.4 / paperweight validation bug.)
4. `build-data/leaf.at` may pick up spurious access-transformer churn during a rebuild — revert it
   (`git checkout -- build-data/leaf.at`) unless your change genuinely needs a new AT.
5. Commit the regenerated patch (and any `src/main` files) to the main repo.

Keep one logical change per patch, and put a clear `// Fuji - <what/why>` comment on lines you add to upstream methods.

## Pull requests

- Use a **personal fork**, not an organization (GitHub blocks maintainers from updating org-owned PR branches).
- Keep PRs focused; explain what the change does and how you tested it (especially for cannon/combat changes).
- New gameplay features should be **config-gated and default-off** so they can't change behavior for existing servers.
